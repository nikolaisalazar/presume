Presume has a coherent product idea, a distinctive interface, and useful engineering foundations. It needs a focused reliability pass before it meets the combined standard of portfolio quality and dependable everyday use. The most consequential problems affect the promise at its center: users can lose edits, delete the wrong content, and export a document that differs materially from the editor.

This audit reviewed `main` at `c52e175` on September 10, 2026. It covered the application, document model and persistence, formatting, PDF and JSON export/import, review client and service, accessibility, product workflows, dependencies, tests, CI configuration, and documentation. Application code was left unchanged. All interactive experiments used synthetic resumes and isolated browser contexts.

There are **19 prioritized findings: eight P1 and eleven P2**. P1 means fix before recommending the editor for dependable everyday use; P2 means a material correctness, usability, accessibility, or operational issue to address next. Dependency advisory severity is distinguished from the priority of the issue in this application. F19 was added during the follow-up [product and landing assessment](2026-09-10-product-and-landing-audit.md), which provides deeper coverage of positioning, copy, visual quality, product journeys, and the proposed order of work.

**F01 · P1. Overlapping delete controls remove the wrong bullet.** The default desktop resume has 28px-high delete buttons spaced approximately 13.64px apart. Hit testing the center of the first Experience bullet's button resolves to the second bullet's button. An actual coordinate click deleted that second bullet. With touch emulation, the buttons grow to 44px while the fitted bullet spacing falls to approximately 10.40px; the first button's center resolves to the third bullet. These deletions immediately autosave. Removing an entire section and pressing Cmd+Z also failed to restore it.

Evidence is in [the delete-button positioning](../../src/styles/app.css#L699), [control sizing](../../src/styles/app.css#L568), and [the delete action](../../src/components/Bullet.tsx#L39). Axe independently reported ten partially obscured targets in the default editor. The [WCAG target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) applies to the usable target area, not just the CSS dimensions. Give each displayed action an exclusive hit area, consider showing a contextual action for the active bullet, and add document-level undo for structural edits. Acceptance should include real coordinate clicks at the minimum font size and with coarse-pointer sizing, followed by undo and reload checks.

**F02 · P1. Fit measures application controls as resume content.** `measurePageHeight` reads the complete live `.resume-page`, including Add bullet, Add entry, and Add section rows. Those rows occupy document flow; the PDF renderer omits them. Empty-field placeholders and heading rows also differ between the two representations. Consequently, a user sees inflated spacing and can be told to shorten content that already fits in the PDF.

A synthetic resume with twelve entries and two short bullets each, using one page, three lines per bullet, and an 8px minimum, measured **1,245.09px** and displayed a page-overflow warning. Its exported PDF occupied **one page**. Temporarily hiding editor-only elements in the diagnostic browser reduced the live page to **1,056px**. A 36-entry fixture warned that it exceeded three pages while exporting to two. The default resume also places Technical Skills much farther down the editor than the PDF.

See [the measurement adapter](../../src/useResizeEngine.ts#L89), [action-row layout](../../src/styles/app.css#L644), [entry actions](../../src/components/Entry.tsx#L83), and [the PDF layout](../../src/pdf/ResumePdfDocument.tsx#L179). Keep controls outside measured document flow and establish a content-only layout contract across editing, fitting, and export. Test actual PDF page counts and text positions against the editor for sparse, dense, and multipage resumes. Simply hiding controls during measurement would leave the visible editor misleading, so the presentation needs to agree too. Page boundaries and actual exported page count should become visible product information.

**F03 · P1. The editor accepts rich content but saves plain `textContent`.** Typing `Alice`, Enter, then `Smith` displays two lines but saves `AliceSmith`. Reloading removes the break and joins the words. This reproduced in Chromium, Firefox 151, and WebKit 26.5. Pasting a red, 48px, bold name retained the pasted HTML and styling in the editor, while saved JSON contained only the text. The visible formatting is absent from the canonical PDF and disappears on reload.

[EditableText](../../src/components/EditableText.tsx#L25) skips synchronization while focused and extracts `textContent` on input and blur. It has no paste normalization or explicit newline policy. Establish plain-text editing semantics, normalize paste and line breaks consistently, and preserve selection and IME composition while doing so. Single-line fields should handle Enter deliberately; any supported multiline field needs matching storage, measurement, and PDF behavior. Verify with real paste and keyboard events, not only programmatic `textContent` assignments. This audit confirmed content and formatting divergence; it did not establish an XSS exploit.

**F04 · P1. A failed save crashes the application.** Replacing `Storage.prototype.setItem` with a function throwing `QuotaExceededError` made the editor's React root empty. Resume and constraint writes are unguarded effects. The landing page also reads storage without protection, and the header's “Saved locally” message is unconditional.

See [storage writes](../../src/storage.ts#L8), [autosave effects](../../src/useResume.ts#L13), [the landing storage read](../../src/App.tsx#L23), and [save status](../../src/components/AppHeader.tsx#L23). Return explicit save outcomes, keep unsaved content usable in memory, and expose a persistent recovery path through export. Distinguish missing, invalid, and inaccessible stored data so a recoverable record is not immediately replaced by the template. Verify quota and access failures after editing as well as during initial load.

**F05 · P1. Multiple tabs silently overwrite each other.** Each editor loads one snapshot, then writes the entire resume after any change. There is no revision check, storage-event handling, or conflict notice. Reproduction: open two tabs; change the name in tab A; change an entry title in tab B. The stored name reverted to the original name from tab B while tab A continued displaying its newer value and “Saved locally.”

[useResume](../../src/useResume.ts#L7) and [saveResume](../../src/storage.ts#L8) own this behavior. Introduce revision-aware writes and a clear response to external edits. A single active editor or explicit conflict-resolution flow would be sufficient for the present scope. Verify two-tab interleavings for both resume content and formatting settings.

**F06 · P1. PDF export corrupts non-Latin identity data.** A synthetic name `李明 — María José` and contact text containing `東京` displayed correctly in the browser. In the PDF, the Chinese name became an unrelated `N`-like glyph and the Japanese text was corrupted. Both rasterized PDF inspection and text extraction confirmed the problem; the accented Latin name survived.

[PDF font registration](../../src/pdf/ResumePdfDocument.tsx#L22) registers only EB Garamond variants, while the browser can fall back to other installed fonts. The import model accepts these characters without warning. Provide supported-script fallback fonts in the PDF path or detect unsupported glyphs before export and offer a useful remedy. Cover names, contact text, and body text with representative script fixtures, checking visible glyphs and extracted text. A PDF containing the wrong candidate name is a document-integrity failure.

**F07 · P1. Editable fields lack an accessible editing contract.** Chromium's accessibility tree exposes all **48 focusable editable fields** in the default resume as unnamed generic rich-text elements. Empty fields rely on CSS-generated placeholders rather than accessible labels. Keyboard tabbing can reach the fields, but their purposes and relationships are not reliably named for assistive technology. Resume section labels are also editable spans rather than a navigable heading structure.

The shared cause is [EditableText](../../src/components/EditableText.tsx#L3), used by [ResumeHeader](../../src/components/ResumeHeader.tsx#L15), [Section](../../src/components/Section.tsx#L39), [Entry](../../src/components/Entry.tsx#L36), and [Bullet](../../src/components/Bullet.tsx#L37). Add meaningful field names, appropriate textbox semantics and multiline state, and document structure that remains understandable while editing. Check the resulting experience with VoiceOver or NVDA. This finding follows the [WCAG name, role, and value guidance](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html); an actual screen-reader session remains an acceptance check.

**F08 · P2. PDF pagination can orphan an entry heading.** With eighteen synthetic entries, two short bullets per entry, and global scale 0.8, page one ended with Engineering role 18, its date, company, and location. Page two contained only that entry's two bullets. The intended first-bullet reservation does not consistently keep the heading with its content.

See [the reservation calculation](../../src/pdf/ResumePdfDocument.tsx#L158) and [heading/bullet wrapping](../../src/pdf/ResumePdfDocument.tsx#L189). Existing coverage validates a particular boundary at scale 1.0583984375. Extend the pagination contract across scales and boundary positions, preserving heading plus initial body content while still allowing oversized bullets to wrap. Treat the actual PDF output as the test oracle.

**F09 · P2. A JSON backup does not preserve document formatting.** Export serializes only `Resume`. Importing that backup into a fresh browser preserves text but applies default constraints. A real export/import round trip changed `{maxPages: 1, maxLinesPerBullet: 3, minFontSize: 12}` to `{maxPages: 1, maxLinesPerBullet: 1, minFontSize: 8}`, changing the chosen scale from **1.2 to approximately 1.0496**.

See [JSON export/import](../../src/export.ts#L27). The current behavior matches the narrow resume-data schema, but it falls short of the product's portable-backup use case. Introduce a versioned backup envelope containing resume data and constraints, with backward-compatible import of existing files. Verify restore into a fresh browser against both settings and the resulting PDF.

**F10 · P2. A failed review rerun loses the stale warning.** Start from a successful review, rerun it, edit the resume while the request is pending, and return a review error. The previous result stays visible but the “Review is stale” warning disappears. The error handler restores the stale flag captured at request start instead of retaining the edit that occurred during the request.

See [the error transition](../../src/useResumeReview.ts#L158). Compute staleness from the stored result's document revision and the current revision, or preserve it through a functional state transition. Add this specific success → rerun → edit → failure sequence to the review-state tests. The existing stale-before-rerun case does not cover it.

**F11 · P2. Review cannot recover from failed discovery without remounting.** Configuration is fetched only on mount. A discovery failure leaves the Review action disabled with no Retry connection control. Both configuration and review requests also lack an explicit client deadline or cancellation signal. The client discards the advertised review timeout, and a pending request has no user cancellation path.

See [configuration discovery](../../src/useResumeReview.ts#L59), [the request guard](../../src/useResumeReview.ts#L124), and [network calls](../../src/reviewApi.ts#L73). Provide an explicit availability retry, cancellation, and a deadline consistent with the service's documented processing window. Do not automatically resubmit costly review POSTs. A backend becoming reachable should be recoverable from the open editor.

**F12 · P2. Users cannot see where Review will send their resume.** The service returns `llmProvider`, `defaultModel`, and `githubEnrichmentEnabled`, but the hook retains only the enabled/disabled decision. With a fixture advertising Gemini and GitHub enrichment, the pre-submission UI showed only “Review resume / Advisory check / Start.” Neither provider nor enrichment appeared. The service documentation explicitly describes hosted-provider transmission, so this information matters to someone using a local-first editor.

See [the discarded configuration](../../src/useResumeReview.ts#L61) and [the Review action](../../src/components/ReviewRail.tsx#L88). Retain and display the safe provider and enrichment metadata before submission, including a clear distinction between browser storage and review processing. This is conditional on a configured service; no real resume or synthetic fixture was sent to Gemini or GitHub during this audit.

**F13 · P2. The Feedback tab is empty on the implemented review path.** The adapter always produces `annotations=[]` and empty category suggestions. Overall improvements and strengths do survive, but the UI places them under Score; Feedback is backed exclusively by annotations. A result shaped like the real adapter's output therefore says “No feedback returned” in Feedback despite having recommendations elsewhere. The richer browser fixture supplies annotations that the current adapter cannot produce.

See [adapter normalization](../../review-service/app/hiring_agent_adapter.py#L252) and [Review tab contents](../../src/components/ReviewPanel.tsx#L184). Align the interface with available output: present overall recommendations as feedback, or hide the annotation-specific surface until populated. Any future annotation mapping should remain conservative. Add an end-to-end case generated through the real normalization function.

**F14 · P2. The upload cap does not bound incoming multipart parsing.** FastAPI resolves `UploadFile` before entering the route. The application's chunked reader then limits an already parsed file. Instrumenting `UploadFile.write` with a 1 MiB application limit showed the parser had written all **3,145,737 bytes** of a synthetic upload before the route returned 413. The adapter correctly remained uncalled.

See [the route and reader](../../review-service/app/main.py#L79). Enforce request size before or during body consumption, including chunked requests, and retain the route-level limit as a second boundary. The documented external proxy limit is useful; make its necessity and the application limit's scope explicit. Account for multipart overhead, additional parts, temporary disk use, and concurrent requests. The existing test proves a 413 response, not early rejection.

**F15 · P2. Dependency updates need an explicit maintenance path.** The pinned backend resolves FastAPI 0.115.6, Starlette 0.41.3, and python-multipart 0.0.20. The upload endpoint uses the parser affected by [unbounded multipart-header denial of service](https://github.com/Kludex/python-multipart/security/advisories/GHSA-pp6c-gr5w-3c5g). Starlette also falls within the [file-spooling event-loop blocking advisory](https://github.com/Kludex/starlette/security/advisories/GHSA-2c2j-9gv5-cj73). Upgrade to a compatible maintained dependency set and verify the API contract after doing so. These service issues deserve higher urgency if the endpoint is exposed to untrusted callers.

`npm audit` reported 19 dependency entries: one critical, eleven high, six moderate, and one low. These counts do not describe nineteen exploitable bugs in the deployed static site. The critical entry is Vitest 3.2.4 and concerns an exposed test UI/API or relevant Windows modes; the checked-in CI uses ordinary test runs. See the [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp). Several other findings belong to build tooling and the shadcn CLI. `pip-audit` flagged three package names; its raw output contains duplicate advisory records. Keep runtime exposure separate from scanner counts, refresh [the dependency pins](../../review-service/requirements.txt#L1) and [the npm lockfile](../../package-lock.json), and add a repeatable advisory check. No CVE exploitation was attempted against a deployed service.

**F16 · P2. Active document controls are too faint at rest.** Measured on the white resume, the remove control's `rgb(51,65,85)` at 0.34 opacity composites to approximately `rgb(186,190,197)`, yielding **1.86:1** contrast. Add-control text at 0.68 opacity yields **3.51:1**. The visible text is 11px after the document transform, despite its larger computed layout font size. These are usable controls, so disabled-control exceptions do not apply.

See [control opacity and colors](../../src/styles/app.css#L568). Keep resting controls legible while preserving the restrained visual system. Normal text needs 4.5:1 under [WCAG text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html); identifying control graphics need 3:1 under [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html). Test composited colors and actual presentation size, including transforms, rather than only theme-token pairs.

**F17 · P2. The bottom landing CTA opens the editor near its bottom.** Clicking the ending section's edit action at a 1280×800 viewport left `scrollY=708`; the resume name was 371px above the viewport and the document toolbar was 521px above it. Focus fell to `body`. The route changes but its scroll and focus state are inherited from the long landing page.

See [route transitions](../../src/App.tsx#L30) and [the ending CTA](../../src/components/LandingPage.tsx#L189). Define scroll and focus behavior for editor entry and back navigation. Test both landing CTAs and keyboard activation, with an assertion that the editing starting point is visible and meaningfully focused.

**F18 · P2. Configuration readiness overstates actual service readiness.** `hiring_agent_available` checks only whether a directory exists. This workspace has Hiring Agent checkout `4db8655`, but no checkout virtual environment or running local Ollama endpoint was available. With explicit local-provider settings and an intentionally unavailable local Ollama address, `/config` still returned `reviewEnabled: true` and `reviewReadiness: ready`; an actual adapter invocation returned a safe 502 in approximately 43ms.

See [readiness calculation](../../review-service/app/config.py#L47) and [interpreter selection](../../review-service/app/hiring_agent_adapter.py#L159). Check the entrypoint, interpreter and necessary imports at startup, and provide a bounded provider/model availability check where appropriate. Alternatively, name the existing signal as configuration validity rather than runtime readiness. Keep diagnostic responses allowlisted and free of paths or credentials. This would make the documented local setup considerably easier to troubleshoot.

**F19 · P1. Reduced motion changes the document's fitted output.** In a fresh Chromium context at 1280×900 with `prefers-reduced-motion: reduce`, the untouched sample settled at global scale **0.8** and reported that it exceeded one page at the minimum font size. Waiting for fonts and editing the name did not resolve the warning. With normal motion preference, the same default document fitted at **1.049609375** without a warning. The smaller scale is also passed to the PDF renderer.

The [universal reduced-motion rule](../../src/styles/app.css#L1897) assigns a nonzero `transition-duration: 0.01ms` to every element. On the resume page, the default transition property is `all`, so this enables transitions for geometry that otherwise changes immediately. [Fit temporarily changes the layout/presentation scales](../../src/useResizeEngine.ts#L30) and synchronously reads the resulting bounds. In a diagnostic browser, overriding transitions to `none` and triggering recomputation restored scale 1.049609375 and removed the warning; the same override did not change the normal-motion result. This isolates the interaction between transitions and synchronous measurement. Disable document-geometry transitions during measurement and ensure the reduced-motion policy does not introduce them. Compare chosen scale, warnings, and PDF output for the same resume under both motion preferences. See [the paired diagnostic results](evidence/2026-09-10/reduced-motion-fit.json).

The broader product assessment follows from these findings. Presume's strongest proposition is direct ownership of a finished document, with local persistence and advisory review. The current landing page communicates that purpose coherently, identifies its sample review as a fixture, and keeps its optional service boundary visible. The typography, restrained palette, fixed paper, theme behavior, and deliberate layout form a recognizable product. Preserve those strengths while improving what the user can trust.

For everyday use, the next product work should make the current document state observable and recoverable: saved versus unsaved, undo for destructive operations, current font size, actual page count, visible page breaks, and a complete backup. The default exported bullet size in Chromium was about **7.87pt**; the 8px minimum permits **6pt** text. The UI labels pixels correctly, but points and the actual fitted size would be more useful when judging a printed resume. Sections and entries can be added or removed, but there is no direct reordering or resume-variant workflow. Those are sensible next capabilities after the integrity defects are fixed. PDF/DOCX import and cloud accounts are documented non-goals, so their absence is not a defect in this audit.

For portfolio presentation, the immediate opportunity is stronger proof of the core workflow. Show an authentic edit → fit → export sequence after the layout contract is repaired, and offer a direct link to this project's repository; the footer currently links to the author's GitHub profile. Review should visibly reflect what the shipped adapter returns. In the checked-in Pages deployment workflow, the production build receives no review endpoint, so the normal static artifact presents Review as unavailable. A clearly documented local demonstration or recorded real-service example would let a reviewer assess that part of the engineering without first provisioning a model. The broader review rubric is geared toward software engineering; make that audience clear wherever the score is introduced.

The architecture is worth retaining. Pure resume operations, typed data validation, the isolated formatting function, lazy client-side PDF rendering, generated review contracts, and the Hiring Agent adapter are useful boundaries. The most valuable changes would strengthen three existing boundaries: a document session that owns revisions, undo and persistence outcomes; a content-only document layout shared by Fit and export; and a review session that associates each result with the exact reviewed document. Keep React/Vite and the existing pure modules while doing this work.

Maintenance is uneven around those boundaries. `app.css` is 2,274 lines and contains application, document-control, landing, and review rules; browser layout is affected by styles beyond `resume.css`. Splitting by responsibility would make changes easier to assess. Several tests assert exact CSS strings, selectors, workflow versions, and presentation values. Those checks can protect intentional design decisions, but the passing suite missed actual hit targets, persisted text semantics, page fidelity, and stale-state transitions. Put more verification effort into those user-visible outcomes. The PDF chunk is approximately 1.47 MB uncompressed / 492 KB gzip, with about 2.59 MB of emitted Garamond font assets; lazy loading is already useful. Font subsetting and route-level loading are secondary optimizations after correctness, with glyph-coverage tests guarding any font changes.

There are additional operational and documentation details to tighten. The root setup instructions do not declare the working Node runtime: on this machine, Node 26.7.0 produced 31 storage-related test failures, while Node 24.21.0 passed all 232 frontend tests. Add a local runtime declaration and a root setup path for the Python environment; the CI already specifies Node 24 and Python 3.11. The Hiring Agent setup clones an unpinned external checkout, making compatibility and installation less reproducible. Some product documentation still describes the older PDF approach as Letter-height segmentation. The README names MIT but no root license file is tracked. Error normalization also has an uncovered edge: a string form field submitted as `file` returns FastAPI's ordinary 422 `detail` response, including the submitted synthetic value, rather than the advertised error envelope. Decide whether to normalize it or document it as a separate contract.

The service explicitly targets trusted local or self-hosted use with external controls. That is a valid scope for this product. CORS should not be mistaken for request authorization: an in-process test with an unapproved Origin still invoked the adapter and returned 200 without an allow-origin header. This confirms server behavior, not whether a particular browser will permit a request to a local network address. Keep authentication, rate/concurrency controls, and proxy limits explicit prerequisites for an untrusted deployment. Safe exception messages, subprocess environment filtering, temporary-directory cleanup, and disabling upstream development caches are strengths already present in the code.

The recommended order of work is:

1. Protect content: exclusive delete targets, structural undo, normalized plain-text editing, explicit save outcomes, and multi-tab conflict handling.
2. Make the document trustworthy: remove controls from document flow, correct reduced-motion measurement, repair glyph coverage and pagination, and preserve formatting in backups.
3. Complete the editing experience: named accessible fields, resting contrast, route focus/scroll behavior, and visible page/font information.
4. Align Review with its implemented capabilities: reliable stale tracking, recovery and deadlines, provider disclosure, useful Feedback, and accurate readiness.
5. Refresh vulnerable dependencies and strengthen early upload controls, then update tests and documentation around these behaviors.

Presume's next milestone should demonstrate that an ordinary user can edit, recover, reopen, and export exactly the document they intended. That would materially improve both its day-to-day value and its credibility as a portfolio project.
